ヴェスペラ：move_location呼び出しを確認

ヴェスペラのアスモデウス×バルバトス会話で、移動の決定的な処理を確認。アスモデウスが『じゃあ俺がそっちへ行く』『すぐに行くよ』と約束した後、会話ログ内に `move_location(destination="紅茶店「宵闇」")` が明示的に出現している。

この直後、アスモデウスは『やっと着いたか』と到着描写を行い、『―― アスモデウスは紅茶店「宵闇」に到着した ――』と表示。world_stateでは同時刻2026-07-10T10:02:08に movement: riverside→tea_house、eventsにも tags:['moved'] の単独イベントが記録され、character.locationもtea_houseへ更新されている。

したがってmovementは単なる自然言語の推測ではなく、会話生成中に標準の `move_location` アクション／ツールが呼ばれることでworld_stateへ反映される仕組みと考えてよい。

バルバトス側は既に目的地が紅茶店『宵闇』だったため、『目的地は既に…』と応答して移動しなかった。move_location処理は現在地を参照し、同一地点への移動を抑止する。

この発見により、『locationがnullだとmove_locationが使えない可能性』がさらに重要になった。エリュシオンでは会話中に移動の約束や外出宣言が何度もあったが、move_locationの明示呼び出しは一度も観測されず、全character.location=nullのまま。

ヴェスペラの『住民の動静』タブには、立ち聞き・移動履歴・噂がまとめて表示される。移動履歴にはアスモデウスの川辺→紅茶店、カイムの深い森→古書店が表示され、world_stateと一致。

カイムの通常会話履歴が現UIにはない一方で、立ち聞き断片とmovementが残っているため、カイムの移動時にも同様のmove_locationが、保存されていない／別系統の会話・自律会話内で呼ばれた可能性が高い。

ヴェスペラの立ち聞きには、ユーザーが通常会話させていない組み合わせも複数存在する。これは自律会話または別系統の会話生成が存在する可能性を示すが、現時点では仕組み未確定。

AsmodeusはHalphasに『こっちへ来ればいいだろ』と紅茶店「宵闇」へ誘った。

Halphasは『すぐには行けねえが、この支柱の様子が落ち着いたら、真っ先にそっちへ向かう』と返答。これは即時移動の確定ではなく、条件付きの未来予定。

このため、この回でmove_locationが出なかったことは『現在のVesperaでもmove_locationが壊れている』証拠にはならない。

途中でscene event『甘い紅茶の湯気に混じり、虹色の泡が店内に漂い始めた。』が発火し、紅茶店にいるAsmodeusが反応した。

Vespera world_stateに移動専用の隠しcharacter項目は見当たらない

Vesperaのworld_state全体を確認。characters各人の構造は基本的に `location` と `affinity` のみで、move_enabled・home・route・movement_modeなどの移動専用フィールドは見当たらない。

実移動記録はworld_state直下の `movements` 配列に保存され、各要素は `char / from / to / at`。同時刻にeventsへ `tags:["moved"]` の地点付きイベントも追加される。

Asmodeus移動後の一部scene/birds_listeningイベントには `location:"tea_house"` が入っている。少なくとも同席状態になった後は、その会話場所がイベントlocationとして使われる場合がある。

Vesperaのscene eventも過去にはlocation:nullが多数あるため、scene eventのlocation有無そのものはmove_location機能の前提ではない。

次の確認候補として、Elysionのraw JSONに `movements: []` が実際に存在するかを確認する価値がある。概要表示の『0件』だけでは、空配列が存在するのか、キー自体が欠けていて0扱いされているのか区別できない。もしキーが欠けていれば、標準move helperが既存配列を前提としている実装差の可能性を検討できる。

Elysionにもmovements空配列が存在・初期化差仮説を否定

Elysionのraw world_state全体を確認し、`"movements": []` が実際に存在することを確認。

したがって、概要で0件と表示されているだけでキー自体が欠けていた、という仮説は否定された。

root構造としては characters / weather / events / pending_events / overheard / items / movements / rumors / turns_since_event が揃っており、Vesperaと同系統のworld_state構造になっている。

characters各人にもlocationとaffinityがあり、全9人のlocationは有効なElysionマップIDで埋まっている。

Elysion側で実移動が起きない理由は、world_stateのmovements配列欠如やcharacter location未初期化では説明できない。

ここまでのUI比較では、世界観・map・character・ability・world_event・world_stateのいずれにも、Vesperaだけmove_locationを有効にする明示設定は見つかっていない。残る大きな仮説は『現在の本番エンジン全体でmove_location挙動が変わった』か『VesperaだけにUIから見えない内部登録がある』。

turns_since_event=15後のイベント発火

本番 #102 ミモザ×ダフネの続き4ターンで、前回world_stateの turns_since_event=15 から観察を継続。

1ターン目（Daphne）と2ターン目（Mimosa）では出来事なし。その後、3ターン目の直前に pending FIFO先頭の『カフェ・フルールのテラス席に、柔らかな午後の陽光が差し込んだ。』が画面上で発火した。

この配置は『各キャラクターターンの直前にイベント判定』モデルと一致する。15到達で必ず発火する固定しきい値ではなく、15を超えて判定を外すこともある。

また、発火時点で会話はほぼ終了しており、ダフネは図書館、ミモザは広場にいるにもかかわらず、カフェの出来事は二人の発言内容へ直接反映されなかった。scene eventのlocation整合・話題拘束は弱い場合がある。

world_state確認により、イベント #36 の発火時刻は 2026-08-09T14:11:23 と確定。participants は daphne / mimosa、location は null、tags は scene。

turns_since_event は前回15から、イベント前に16→17まで上昇したのち発火で0へリセットし、その後1ターン分加算されて会話終了時1。少なくとも17までは上がるため、固定しきい値説は否定的。

pending FIFOは先頭のカフェ陽光イベントを消費。新規pending『図書館の窓辺に、一冊の古い詩集が置かれた。』が 2026-08-09T14:11:27 に補充された（発火4秒後）。

イベント本文はカフェ・フルールを明示するが、event.location は null。ダフネは図書館、ミモザは広場におり、会話でもこのカフェ出来事へ直接反応しなかった。scene eventの場所整合性は弱い。

好感度は Mimosa→Daphne 64→68、Daphne→Mimosa 64→68。weatherは夕立・5℃、movementsは0件のまま。

新pending『図書館の窓辺に、一冊の古い詩集が置かれた。』は、直前のDaphneの図書館・古い歴史の本という話題と近い。図書館＋本という直前の会話内容をWeaverが拾って次のpendingへ反映した可能性が高く、これまでの『replacement pendingは直前の会話を反映しやすい』観察を補強する。
